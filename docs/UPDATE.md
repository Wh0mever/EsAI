# Обновление EsAI (прод)

Стек работает в HTTPS-режиме (overlay `compose.yaml + compose.https.yaml`).
Поэтому все команды — с обоими `-f` файлами. Удобно завести алиас:

```bash
cd /opt/esai
alias dc='docker compose -f compose.yaml -f compose.https.yaml'
```

## Обычное обновление
```bash
cd /opt/esai
git pull origin main

# Бэкенд (код примонтирован, но при смене зависимостей/Dockerfile — пересборка):
dc build core            # если менялся requirements.txt/Dockerfile
dc up -d --force-recreate core
# Миграции применяются автоматически на старте core (entrypoint).
# Проверка, что миграции в порядке:
dc exec -T core python manage.py makemigrations --check --dry-run   # ждём "No changes detected"

# Воркеры Celery тоже читают код с диска (./core:/app), но всегда
# ПЕРЕСОЗДАЁМ их, а не `restart`: restart поднимает контейнер с прежними
# настройками и не видит правок compose.yaml (монтирование кода, env,
# stop_grace_period, logging). Контейнер, созданный до монтирования, так и
# крутил бы старый код из образа — без новых задач beat и фиксов биллинга.
# --no-deps — чтобы заодно не пересоздались core и redis. При смене
# requirements/Dockerfile добавить --build.
# celery_media дорабатывает начатые съёмки до 12 минут, celery_vstudio
# (воркер видеостудии) — до 5 минут (stop_grace_period): команда может ждать,
# это нормально. Забыть celery_vstudio — значит оставить видеостудию на
# прежнем коде до следующей выкладки.
dc up -d --force-recreate --no-deps celery celery_beat celery_media celery_vstudio

# Фронтенд (всегда пересобирать образ — Next standalone):
dc build next
dc up -d --force-recreate next
# nginx спрашивает адреса core/next у docker-DNS на каждый запрос, рестарт
# nginx после пересоздания контейнеров больше не нужен. После правки
# nginx/nginx-ssl.conf — только пересоздание (файл примонтирован одиночным
# bind-mount, reload внутри контейнера видит старый файл):
# dc up -d --force-recreate --no-deps nginx
```

## Видеостудия: оплаченный ролик не сохранялся (09.10.2026)

Что сломалось. Первые настоящие ролики студии провайдер снял и взял за них
деньги, а выдача пять раз подряд упала на
`Permission denied: '/app/media/vstudio/<id>'` — дубли ушли в «Оплачено, но не
выдано». Кредиты у людей не списались.

Почему. `core` работает от root, воркеры Celery — от `appuser`, а `chown` из
`entrypoint.sh` проходит один раз, при старте `core`. Каталог, созданный в
`media` позже, получал владельца root и права 755: загрузка фото создавала
`vstudio/` и `vstudio/<id>/`, и воркер студии писать туда уже не мог.

Что меняет исправление (только сервер, миграций и сборки фронтенда нет):
- новые каталоги в `media` создаются с правами 777, файлы — как раньше, 644
  (`FILE_UPLOAD_DIRECTORY_PERMISSIONS`, `FILE_UPLOAD_PERMISSIONS`). Каталог
  человека `vstudio/<id>/` загрузка фото заводит сама и права ставит через
  `chmod`: от `umask` процесса gunicorn (он один на 8 потоков) они не зависят;
- перед платным запросом воркер студии создаёт и стирает пробный файл в
  каталоге человека. Не вышло — провайдеру ничего не уходит: дубль закрывается
  с «Студия временно недоступна. Мы уже чиним. Кредиты не списаны», причина —
  в журнале генераций («хранилище недоступно: …») и в
  `logs/celery_vstudio.log` (строка «хранилище недоступно» с дублем и путём);
- там же воркер смотрит свободное место: пробный файл запишется и на почти
  полный диск, а ролик — нет. Меньше 1 ГБ на диске `media` или во временном
  каталоге контейнера (`/tmp`, туда скачивается ролик) — провайдеру тоже ничего
  не уходит, причина — «хранилище недоступно: мало места: … МБ свободно в …,
  нужно 1024 МБ». Это новый способ студии встать: пока места меньше порога,
  отказ получает КАЖДАЯ генерация, и ролик, и картинка. Порог —
  `MIN_FREE_BYTES` в `core/vstudio/storage_check.py`;
- `logs/django.log` открывается при первой записи, а не при старте процесса.
  Файл делят root (`core`) и `appuser` (воркеры): после ротации, которую сделал
  `core`, он принадлежит root, и воркер, поднятый без перезапуска `core`, не
  стартовал вовсе (`Unable to configure handler 'file'`) — вместе с отправкой
  и опросом оплаченных дублей. Теперь воркер работает, а в его журнале
  (`logs/celery*.log` или `dc logs <воркер>`) идут блоки
  `--- Logging error ---` с `PermissionError … django.log`. Лечится так:
  `dc exec -T core chown appuser:appuser /app/logs/django.log`.

Выкладка — «Обычное обновление», и `core` пересоздаём обязательно: настройка
действует только на новые каталоги, а уже лежащие (root, 755) перевладевает
`entrypoint.sh` при старте `core`. Воркеры тоже пересоздаём — пробу делают они.
```bash
# До выкладки: места, которое видит воркер студии. В колонке Avail обеих строк
# должно быть заметно больше 1G, иначе после выкладки студия откажет всем.
dc exec -T celery_vstudio df -h /app/media /tmp

dc up -d --force-recreate core
dc up -d --force-recreate --no-deps celery celery_beat celery_media celery_vstudio

# 1. Старые каталоги перевладел entrypoint — ждём пустой вывод. Сразу после
#    перезапуска это проверка только chown. Новую настройку она проверяет, если
#    повторить её позже (например, на следующий день, после новых загрузок):
#    вывод по-прежнему пустой.
dc exec -T core find /app/media -type d ! -user appuser ! -perm -002

# 2. То же, что в инциденте, на пробном каталоге: core (root) создаёт новый
#    каталог через хранилище, воркер (appuser) в него пишет. Ждём
#    WORKER-CAN-WRITE; «Permission denied» — права новых каталогов не действуют.
dc exec -T core python manage.py shell -c "from django.core.files.storage import default_storage as s; from django.core.files.base import ContentFile as C; s.save('_permcheck/a/x.txt', C(b'x'))"
dc exec -T celery_vstudio sh -c 'touch /app/media/_permcheck/a/w && echo WORKER-CAN-WRITE'
dc exec -T core rm -rf /app/media/_permcheck

# 3. Тесты с настоящими правами каталогов (на Windows они пропускаются).
#    Только в контейнере воркера: от root два теста пропускаются. Ждём OK без
#    skipped. База не нужна и не создаётся, файлы — во временном каталоге.
dc exec -T celery_vstudio python manage.py test \
  vstudio.tests.test_storage_check.DirectoryModeTests \
  vstudio.tests.test_storage_check.DiskProbeTests \
  vstudio.tests.test_storage_check.FreeSpaceTests \
  vstudio.tests.test_storage_check.UploadDirectoryTests \
  vstudio.tests.test_storage_check.SettingsTests --noinput
```

Потерянные 09.10 ролики можно попробовать довезти после выкладки:

бесплатно; получится, только если провайдер ещё хранит результат.

## Открытие видеостудии всем

У `/video-studio` два независимых выключателя, и порядок важен.

1. **Режим на бэкенде** — ключ `vstudio_mode=on`. Меняется без выкладки и
   действует сразу: admin-new → Настройки → «Видеостудия» → «Для всех» →
   «Сохранить». Значения: `off` — студии нет, `staff` — только сотрудники (так
   по умолчанию), `on` — все. Ключ сильнее `VSTUDIO_MODE` из `.env`; «Как в
   окружении» убирает его. У кого страница студии уже открыта, увидит её после
   обновления страницы.
2. **Сборка фронтенда** с `NEXT_PUBLIC_VSTUDIO_NAV=1` — пункт меню, ссылки на
   студию с главной и из чата, sitemap и индексация. Значение вшивается при
   сборке, поэтому образ пересобираем:
   ```bash
   # в /opt/esai/.env: NEXT_PUBLIC_VSTUDIO_NAV=1
   dc build next
   dc up -d --force-recreate next
   bash scripts/sync-next-static.sh
   ```

Сначала режим, потом сборка. Наоборот нельзя: людей приведёт в студию меню, а
там — «скоро откроется», и эту же страницу проиндексирует поиск.

До шага 1 проверить:
- `dc ps` — работают `celery_vstudio` (сами генерации), `celery` и
  `celery_beat` (снимают зависшие генерации и резервы кредитов);
- у нужных моделей стоит «Показывать в видеостудии» (Django-админка `/admin/`
  → GPT модели), а на счёте OpenRouter больше `VSTUDIO_MIN_PROVIDER_USD`;
- витрина первого экрана собрана: admin-new → «Витрина»
  (`/admin-new/vstudio-showcase`). Пока в ней меньше 5 роликов, карусель
  первого экрана показывает сцены мультстудии (см. «Карусель видеостудии»
  ниже). Ставятся в неё только работы сотрудников: в адресах файлов виден
  номер аккаунта автора.

Лёгкую копию ролика для лент первого экрана (480 px, без звука) собирает
воркер `celery` через несколько секунд после добавления работы в витрину; до
этого и при сбое сборки играет исходник. Собралась ли копия — Django-админка
`/admin/` → «Витрина видеостудии», колонка «Лёгкая копия»; там же действие
«Пересобрать лёгкую копию ролика».

Откат. Режим — там же, «Только сотрудники» или «Выключена»: действует сразу.
Уже запущенные генерации при этом доезжают и оплачиваются как обычно. Меню и
индексация уходят только новой сборкой: `NEXT_PUBLIC_VSTUDIO_NAV=` (пусто) и те
же три команды.

## Карусель видеостудии: 12 сценариев

Карусель первого экрана `/video-studio` показывает ролики самой студии, по
одному на сценарий: киносцена, реклама товара, персонаж, автомобиль, экшен,
фантастика, fashion, музыкальный клип, Image → Video, анимация, реалистичная
сцена, Reels / TikTok. Блока «Сделано в EsAI» под ней больше нет. Сервер и
фронтенд выкладываются вместе, как в «Обычном обновлении».

- Миграция `vstudio 0004` применяется сама на старте `core` и таблицу не
  меняет: «Раздел» работы стал «Сценарием», прежние «Соцсети» и «Аниме»
  переезжают в «Reels / TikTok» и «Анимацию». Откат — `migrate vstudio 0003`:
  ключи возвращаются, а работы сценариев, которых раньше не было, уходят в
  «Другое».
- Сценарий работе ставят там же, где её добавляют: admin-new → «Витрина».
  Карусель переходит на ролики студии, когда видимых роликов в витрине не
  меньше 5; до этого в ней сцены мультстудии. Вперемешку они не идут.
- **«Показывать запрос» теперь открывает больше.** С этой галочкой гость видит
  текст запроса и параметры (по ним работает «Снять похожее»), а у работы,
  снятой с первого кадра (Image → Video), — ещё и картинку этого кадра.
  Референсы и последний кадр не показываются никогда; без галочки наружу не
  идёт ни запрос, ни кадр. Кадр, который автор удалил из своих материалов,
  пропадает с сайта сразу. Какой именно кадр станет виден, показывает сама
  панель: в окне «В витрину» под галочкой и в строке работы рядом с
  переключателем. То же — в Django-админке `/admin/` → «Витрина видеостудии»,
  страница работы, строка «Первый кадр».
- Ролики сценариев снимает команда `vstudio_shoot_showcase` — настоящими
  дублями сотрудника, на его кредиты. Аккаунт — сотрудник на платном тарифе;
  студия включена хотя бы для сотрудников, `celery_vstudio` работает.
  Сначала пробный прогон: он ничего не пишет и не тратит, а показывает модель,
  параметры и цену каждого сценария, итог и хватает ли баланса.
  ```bash
  dc exec -T core python manage.py vstudio_shoot_showcase --user <почта сотрудника> --dry-run
  dc exec -T core python manage.py vstudio_shoot_showcase --user <почта сотрудника> --yes
  ```
  Одновременно снимается столько роликов, сколько аккаунту разрешено держать
  открытыми (обычно два); готовые работы встают в витрину скрытыми —
  посмотреть и включить их можно в admin-new → «Витрина». `--publish`
  показывает сразу, но только работы, которые ставит этот же запуск: строку,
  уже стоящую в витрине, команда не включает (в итоге есть строка «В витрине:
  показываются — N, скрыты — M»). Оборвалось или кончилось ошибкой — та же
  команда ещё раз: с той же меткой она ничего не переснимает, а подхватывает
  начатое. Переснять сценарий — `--only film,ad --label v2`; пустой `--only`
  команда не принимает. Сценарий, для которого нет открытой модели с его
  пропорциями (вертикальный ролик — 9:16), в плане помечен «нельзя» и не
  снимается.

## Карусель видеостудии: сколько роликов показывать

Раньше карусель первого экрана брала из витрины не больше 12 роликов. Теперь
это настройка: admin-new → «Витрина» → «Роликов в карусели», от 5 до 48, пока
не меняли — 12. Сохраняется сразу, без выкладки и перезапусков; правка видна в
журнале действий (`settings.edit`, ключ `vstudio_reel_size`).

- Миграций нет: значение лежит в runtime-настройках (ключ `vstudio_reel_size`),
  меняется только из панели витрины. Сервер и фронтенд выкладываются вместе,
  как в «Обычном обновлении». Сайт переживает любой порядок: прежний фронтенд
  новое поле не читает и показывает 12, новый фронтенд со старым сервером —
  тоже 12. Сама настройка в панели работает, когда выложены обе части.
- Сервер отдаёт новое значение сразу после сохранения (в худшем случае — через
  полминуты, столько живёт кэш настроек). Посетитель видит его со следующей
  загрузки страницы студии; уже открытая вкладка помнит карусель до 10 минут.
- Роликов в карусели не больше, чем включено в витрине: настройка 48 при 12
  включённых работах покажет 12.
- Откат — поставить там же 12. Проверка после выкладки (ждём `"reel_size":12`
  или то число, что стоит в панели):
  ```bash
  curl -s https://esai.kg/api/vstudio/showcase/ | grep -o '"reel_size":[0-9]*'
  ```

Под «Инструментами режиссёра» на `/video-studio` появился блок «Тренды» —
сетка роликов, которые владелец отобрал сам: восемь карточек, остальные — по

- Работа витрины стоит в одном месте: «Карусель» или «Тренды». admin-new →
  «Витрина»: поле «Куда» в окне «В витрину» и в строке каждой работы,
  отдельный список «Тренды» и счётчик «В трендах N из 24». В Django-админке
  `/admin/` → «Витрина видеостудии» — колонка и фильтр «Куда». В «Тренды»
  ставятся только ролики, сценарий им не нужен; новые выше.
- Миграция `vstudio 0005` применяется сама на старте `core`: все прежние работы
  остаются в карусели. Откат — `migrate vstudio 0004` (колонка уходит, работы
  «Трендов» возвращаются в карусель).
- Сервер и фронтенд выкладываются вместе, как в «Обычном обновлении». Сайт

  карусель («Тренды» он не видит), новый фронтенд со старым сервером — карусель

- Проверка после выкладки: ответ сайта несёт список `trends` (ждём

  `/video-studio` (уже открытая вкладка помнит витрину до 10 минут).
  ```bash
  curl -s https://esai.kg/api/vstudio/showcase/ | grep -o '"trends":\['
  ```

## Мультстудия: сцены библиотеки из админки

Владелец сам заводит, правит, публикует и снимает с публикации сцены
библиотеки мультстудии и её разделы: admin-new → «Сцены мультстудии»
(`/admin-new/studio-scenes`, API `/api/manage/studio/scenes/` и
`/api/manage/studio/sections/`). В «Работах» у своей сцены пользователя
появилась кнопка «Опубликовать как новую сцену». Каждая правка пишется в журнал
действий (`settings.edit`, ключи `cartoon_preset` и `cartoon_section`).

- Миграций нет. Сервер и фронтенд выкладываются вместе, как в «Обычном
  обновлении»; воркер `celery` пересоздаётся там же — без этого новые превью
  останутся без лёгкой копии (задача `cartoon.tasks.build_preset_preview` идёт
  в общую очередь).
- Превью: mp4 до 24 МБ (nginx пускает 25 МБ вместе с формой), от 1 до 20
  секунд. Лёгкую копию для ленты, обложку и миниатюру собирает `celery` за
  несколько секунд; до этого лента играет сам ролик. Не собралось — в панели
  видна причина и кнопка «Пересобрать».
- Новая сцена берёт модели кадра и видео, качество у первой готовой сцены
  библиотеки, стиль — по аудитории. Модель в форме не выбирается.
- Переводов в один клик нет: в проекте нет переводчика на модели, EN и KG
  заполняются руками. Пусто — на сайте показывается русский текст.
- **Скрытый раздел теперь прячет и свои сцены.** Раньше пропадала только
  вкладка раздела, а его сцены оставались во «Всех» и в «Выборе EsAI». До
  выкладки проверьте, что таких сцен нет (ждём `0`; иначе после выкладки они
  пропадут из библиотеки — откройте раздел или перенесите сцены):
  ```bash
  dc exec -T core python manage.py shell -c "from cartoon.models import CartoonPreset as P; print(P.objects.filter(is_active=True, category__is_active=False).exclude(preview_video='').count())"
  ```
- Сцену, которую уже взяли в мультфильм, удалить нельзя — только снять с
  публикации: готовые мультфильмы пользователей остаются целы.
- `seed_presets` больше не трогает сцены и разделы, которые правили люди — в
  панели или в Django-админке, — даже с `--force`; не прячет разделы владельца
  и не возвращает сцены, удалённые в панели. Сцены из кода, которых никто не
  касался, команда обновляет как раньше.
- «Опубликовать как новую сцену» создаёт сцену снятой с публикации: владелец
  правит названия и публикует её сам. Ролик и кадр копируются к превью
  библиотеки. Отказ, если в сцену могло попасть личное: свой персонаж
  пользователя, реплика (его слова звучат в ролике; реплику, стёртую после
  съёмки, тоже — ролик тот же, сцену надо переснять) или кадр, нарисованный «с
  оглядкой» на прошлую сцену человека. Повторный клик — в том числе после
  перезагрузки и после правки промптов новой сцены — отдаёт уже созданную.
- Файлы превью, которые панель записала сама, при замене ролика, пересборке и
  удалении сцены стираются. Ролик и кадр сцены пользователя («Сделать превью
  сцены») и оплаченные ролики `render_previews` остаются на диске.
- Запасной путь — Django-админка `/admin/`: «Пресеты сцен» (в форме теперь
  есть раздел, аудитория, «Выбор EsAI» и переводы) и «Разделы библиотеки»
  (раньше их там не было). Лёгкую копию и миниатюру она сама не собирает.
- Откат — прежний код. Сцены и разделы, заведённые в панели, остаются обычными
  строками библиотеки и правятся в Django-админке.
- Проверка после выкладки (ждём `401` — ручка есть и закрыта входом):
  ```bash
  curl -s -o /dev/null -w '%{http_code}\n' https://esai.kg/api/manage/studio/scenes/
  ```

## Разово: старые вложения чата

До проверки расширений загрузка чата сохраняла файл под любым именем от
клиента, так что в `media/uploads/chat` могут лежать `.html`, `.svg`, `.rss`,
`.atom` и т. п. nginx их уже отдаёт только на скачивание, но лучше убрать их из
`/media` совсем. Не удаляем, а переносим в карантин вне `/media` — на них
ссылается старая история чатов (там они станут 404).

```bash
cd /opt/esai
# 1) посмотреть, что не проходит нынешний allowlist загрузки чата:
find media/uploads/chat -type f ! -iregex '.*\.\(jpe?g\|png\|gif\|webp\|bmp\|heic\|heif\|pdf\|docx?\|xlsx?\|pptx?\|txt\)' -print
# 2) перенести их в карантин с сохранением путей:
find media/uploads/chat -type f ! -iregex '.*\.\(jpe?g\|png\|gif\|webp\|bmp\|heic\|heif\|pdf\|docx?\|xlsx?\|pptx?\|txt\)' \
  -exec sh -c 'q=$0; for f; do mkdir -p "$q/$(dirname "$f")" && mv "$f" "$q/$f"; done' /opt/esai-quarantine {} +
# 3) остальной /media — только просмотреть (там могут быть законные SVG, их не трогать вслепую):
find media -type f -iregex '.*\.\(rss\|atom\|kml\|xspf\|mml\|x?html?\|shtml\|xht\|svgz?\|xml\|xsl\|m?js\)' -print
```

# 4) После выкладки nginx и карантина — сбросить кэш Cloudflare (Caching →
# Configuration → Purge Everything или Custom Purge по адресам из шага 1).
# SVG Cloudflare кэширует, а `/media/` отдаётся с `expires 7d`: без сброса
# старый ответ (без attachment и песочницы) ещё до недели живёт на краю сети,
# в том числе у перенесённых в карантин файлов.

> Перед крупным обновлением сделайте бэкап БД: `bash scripts/db-backup.sh`.
